# T131 — the app is slow to load during sync (2026-10-19)

Landry, 2026-10-19: "the app is becoming unbearably slow to load, what seems like during syncing."
Since T111 the app library holds the DaVinci catalogue (1,132 `library_type` rows: 501 placeable
types, 631 accessories, ~3 aliases each, JSON cables and accessories; 1.4 MB of JSON in all).

## Measurement

`app/src/perf/t131.perf.test.ts` (runs with the app suite; `T131_LIBRARY=<n>` sets the library
size) replays the Tower master (`fixtures/master-ops.json`, 1,461 ops) and a synthetic library of
the catalogue's shape into a Node store over better-sqlite3 — the JS-side floor; expo-sqlite adds
a round trip per statement and Hermes runs string-heavy code several times slower than V8.

| Step | Before (1,132 types) | No library | After (1,132 types) |
|---|---|---|---|
| Library pull, 1,132 creates in 3 pages (`applyRemoteMany`) | 198 ms (0.18 ms/op) | — | 213 ms |
| Master pull, 1,461 ops | 181 ms (0.12 ms/op) | — | 218 ms |
| Levels home read model (`listProjects` + `loadProjectHome` + `loadLockTable`) | 81 ms | 3 ms | 20 ms |
| `RuleEngine.loadSnapshot` | 13 ms | 20 ms | 15 ms |
| First rules run (42 ops written) | 474 ms | 28 ms | 53 ms |
| **Quiet rules run (nothing to write)** | **500 ms** | **7 ms** | **32 ms** |
| Quiet sync cycle (library stream + project, empty pulls) | 0.2 ms | — | 0.3 ms |

## What it was

1. **A full scan of the library per device lookup.** `findDeviceType` (packages/rules) found a
   device's type by Device text by copying every type into an array and testing the model and
   every alias with a regex key — ~4,500 string operations per call — and `deviceRole`,
   `governingCables`, `deviceNeedsNeuronId` and the lints call it per device per rule (R2c's
   EBDK pairing per device per device). A quiet run went from 7 ms to 500 ms on V8 with the
   catalogue, so seconds on the iPad, **synchronous on the JS thread**: the UI froze for that
   long after every pull that brought ops, after every local edit (debounced 500 ms) and once per
   project at launch. The app's own read models (plan, dashboard, drafts, placement) call the same
   function per device.
   **Fix:** the map of types is indexed by model key once (a `WeakMap` beside the map, rebuilt if
   the map's size changes); a lookup is a map get. Same answers (`library.test.ts`).
2. **A library pull ran the rules on the stream, not on the projects.** The trigger collected the
   project ids of applied ops; the app library's ops carry the stream id (D184), so a library
   pull evaluated an empty "project" (loading the 1,132 types for nothing) and the projects whose
   rules read the library (R2g, R3c) were not re-run. **Fix:** a stream change re-evaluates every
   project and never the stream.
3. **A 500-op pull page in one transaction.** The iPad has one SQLite connection; a screen's
   query waits for the transaction in progress, so a first library or project pull held the
   connection for the whole page. **Fix:** `applyChunk` (default 100 ops per transaction); the
   cursor still moves once per page; a chunk re-applied after a crash is a duplicate.
4. **The log file rewritten on every flush.** The logger read the whole current log (up to
   512 KB) and wrote it back with the new lines appended, synchronously, every 1.5 s while
   anything logged — and the sync engine logs every 5 s. **Fix:** `File.write(text, {append: true})`.

## Seeing the next one

The Sync screen's Connection section has a timing line: `Last cycle 0.4 s · push 0.1 s · pull
0.2 s · apply 0.0 s · 0 pushed, 0 pulled · rules 0.3 s (2 projects, 0 writes)` (`describeCycle`
over `SyncStatus.lastCycle` and `lastRulesPass()`); the `[sync] synced` log line carries `ms`,
`push_ms`, `pull_ms`, `apply_ms`, and `[rules] run` its `ms` per project. Targets (T131): Levels
home within 3 s of launch with a warm store; a quiet cycle under 1 s on the Pipeline project; no
visible stall while a pull runs. The iPad's numbers go on the on-device checklist.
